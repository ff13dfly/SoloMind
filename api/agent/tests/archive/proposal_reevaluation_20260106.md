# 提案重新评估：两步意图检测
日期：2026-01-06

## 背景
*   **初始提案**：将意图检测分为第一步（服务选择）和第二步（方法选择）。
*   **初始结果**：**失败**。错误率高（~80%）。逻辑在第一步就过滤掉了有效的意图。
*   **修正结果（当前）**：**成功**。准确率高。逻辑在第一步正确地过滤掉了无效意图（假阳性），同时保留了有效意图。

## 失败与成功的分析

### 最初为什么失败？
*   **抽象的服务名称**：第一步依赖于通用的名称，如 "crm"、"finance"。
*   **信息丢失**：模型识别语义的“钩子”通常在于**方法名称**（例如，`agenda.create` 暗示“会议”）。在第一步隐藏方法名移除了这个强信号。
*   **结果**：在没有看到 `user.register` 或 `company.create` 的情况下，模型无法自信地将“新员工”与 `company` 服务联系起来，因此默认选择了“聊天”。

### 现在为什么成功？
*   **丰富的描述**：我们在服务层级添加了具体的定义（例如，“仅用于外部实体”）。
*   **负面约束**：明确说明服务**不**用于什么（例如，“不用于内部员工”）将第一步变成了一个高效的**语义防火墙**。
*   **结果**：
    *   **案例 1（“新后端工程师”）**：由于“不用于内部员工”的规则，在第一步被正确拦截。
    *   **案例 19（“不靠谱的客户”）**：由于应用了“无主观判断”的规则，被正确拦截或处理。

## 结论
**两步法是适用的**，但**仅**在满足以下条件时：
> **服务描述必须是“丰富”的，并且包含“负面约束”。**

如果是通用的标签描述（“CRM模块”），单步法（扁平列表）更好。
如果是详细的约束描述（“管理外部客户，而非内部员工”），两步法在扩展性和精确度上更优。

## 建议
建议在生产系统中采用两步逻辑，前提是我们保持在 `api/crm/config.js` 中建立的多语言、基于约束的配置格式。
