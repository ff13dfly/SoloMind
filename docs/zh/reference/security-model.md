# 安全信任模型

> 我们的安全模型是 **"疑罪从有"**——默认网络环境不安全，通过协议层面的密码学保障核心资产。

## 威胁模型

| 攻击类型 | 场景 |
|----------|------|
| **恶意前端** | 山寨 App 钓鱼，诱导输入密码 |
| **恶意后端** | 伪造 Router 返回诱导信息 |
| **中间人攻击** | DNS 劫持，拦截通信 |

## 防御体系

### 第一层：Z-Handshake（零知识握手）

**核心原则**：用户的明文密码永远不通过任何前端发送。

**防御机制**：
```
1. 用户在 App 输入密码
2. 客户端本地 PBKDF2 哈希
3. 服务端返回动态 Challenge
4. 客户端用哈希签名 Challenge
5. 服务端验证签名
```

**攻击分析**：
- 攻击者拿到山寨 App 中输入的密码
- 但无法获取服务端的动态 Challenge
- 即使转发哈希，也只对当次会话有效
- **结论**：密码泄露也无法持久控制账户

### 第二层：代码签名与证书钉扎

**App 签名**：
- 官方 App 经过厂商签名认证
- 私有节点可验证 App 是否官方版本
- 重打包的山寨版无法通过验证

**证书钉扎**：
- 官方 App 内置服务端 SSL 证书指纹
- 中间人攻击会触发证书不匹配警报
- 连接自动阻断

### 第三层：UI 来源强制标识

**安全浮层**：
客户端渲染任何服务端内容时，底部强制显示：
```
当前受控节点：FANG_PUB (官方)
当前受控节点：192.168.1.5 (私有)
```

**防伪机制**：
- 浮层由客户端原生代码绘制
- 后端无法修改或隐藏此标签
- 用户始终知道谁在响应

### 第四层：能力市场认证

**V-认证机制**：
- 上架微服务必须通过静态代码扫描
- 行为审计检测恶意网络连接
- 未认证服务标注"实验性/风险"

**灰度策略**：
- 新服务禁止调用支付等高敏感 API
- 需累积正面评价后解锁权限

## 数据主权保障

```
┌─────────────────────────────────────┐
│  公网 (FANG_PUB)                    │
│  - 可沦陷，但只是入口              │
└─────────────────┬───────────────────┘
                  │ 无法访问
                  ↓
┌─────────────────┴───────────────────┐
│  私有节点 (您的服务器)              │
│  - 本地资产由私钥控制              │
│  - 即使公网入口沦陷也进不来        │
└─────────────────────────────────────┘
```

## 总结

| 攻击场景 | 防御结果 |
|----------|----------|
| 黑客开发假前端 | Z-Handshake 保障，拿不到权限 |
| 黑客开发假后端 | 来源标识保障，无法伪装官方 |
| 中间人攻击 | 证书钉扎保障，连接自动阻断 |
| 恶意微服务 | V-认证保障，高危 API 禁用 |
