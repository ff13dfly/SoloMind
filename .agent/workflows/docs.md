# 文档修改工作流

当修改 `docs/` 目录下的文档时，**必须**按以下步骤执行：

## 1. 修改前检查

- 确认目标文件是否存在中英文两个版本 (`docs/zh/` 和 `docs/en/`)
- 如果只修改一个语言版本，需同步修改另一个版本

## 2. 链接验证

修改文档后，**必须**检查所有内部链接：

// turbo
```bash
cd docs && npm run docs:build 2>&1 | grep -E "(dead link|Error)"
```

如果发现死链接错误：
- 检查被引用的文件是否存在
- 如果目标文件不存在，移除链接或创建目标文件
- 如果文件已被合并/重命名，更新链接指向新位置

## 3. 常见死链接模式

| 原因 | 解决方案 |
|------|----------|
| 文件被删除 | 移除链接或创建 placeholder |
| 文件被合并 | 更新链接指向合并后的文件 |
| 路径错误 | 使用相对路径 `./filename` 或绝对路径 `/zh/path` |

## 4. 协议文档规范

所有协议文档必须遵循统一格式（参考 `docs/zh/protocol/memory.md`）：

```markdown
# 协议名 (English Name)

---

> **协议版本**: 1.0.0  
> **状态**: 稳定 (Stable) / 草案 (Draft)  
> **作者**: Fuu  
> **许可证**: Apache 2.0

---

## 摘要
## 1. 简介 (目的、设计原则)
## 2. 术语定义
## 3. 核心内容...
## 附录 A. 变更日志
```

## 5. 提交前清单

- [ ] 中英文版本同步
- [ ] 本地构建成功（无死链接）
- [ ] VitePress 配置已更新（如有新文件）
- [ ] 侧边栏导航已更新

## 6. Git 提交规范

> [!IMPORTANT]
> **禁止自动提交**：AI 不得主动执行 `git commit` 或 `git push`。

只有当用户**明确表达**以下意图时才执行提交操作：
- "提交"、"commit"
- "推送"、"push"
- "发布到 GitHub"
- "更新仓库"

**提交信息格式**：
```
docs: 简短描述

- 变更点 1
- 变更点 2
```
